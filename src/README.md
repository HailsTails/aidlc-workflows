# src: AI-DLC by bounded context

- One folder per context: `workflow-definition`, `projection`, `packaging`, `installation`, `execution`, `cli`, plus `kernel` for shared identity values and paths and the one implementer per platform capability (file system today), each behind a node-free port file that consumers' narrow ports are declared from.
- Each context has `domain/` (pure types and rules), `application/` (ports and use cases), `adapters/` (IO, Zod at every file and JSON edge) and `fixtures/` (test support only).
- Arrows: Workflow Definition → Projection → Packaging → Installation; Workflow Definition → Execution; the CLI composes the roots. They are data in `src/bridge-map.json`, beside every place a context still reads a legacy `core/` owner and what retires it.
- A context imports another context's `domain/` only; an adapter may also import an upstream `adapters/*-file.ts` file format where the map allows. A port another context or a host implements lives in its context's `application/boundary-ports.ts` (Projection's in `application/ports/<concept>.ts`, one file per Projection concept; the CLI has no application layer, only adapters and the roots in `src/cli/roots.ts`), and only the composition roots import it.
- Host knowledge has one home per harness: `src/hosts/<harness>/` declares its `HostIdentity` and publishes Projection parts, a distribution reader and utility routes through `HostModule`. Projection assembles its `Harness` internally and returns a `HostProjection` value; Packaging layout remains a separate distribution value. Runtime composition uses `RuntimeHost` for Installation's `HostShell` and Execution's conversation, history, decoder and encoder capabilities. Only composition roots import `src/hosts`.
- Composition roots: `src/cli/roots.ts` declares the build and runtime boundaries; `src/cli/main.ts` and `src/cli/package-build-root.ts` bind platform capabilities and context operations. The build root admits the distribution before delegating captured host projection. A projection result carries files and findings, not the root's assembled capabilities or Packaging layout.
- Method sources are read once by Workflow Definition, authored or installed under the host's directory. Every stage, agent, scope, sensor, rule, knowledge document and hook names its file by `MethodSourcePath`, whose folder is fixed by its `MethodSourceKind`; `MethodSources.files` holds each file's bytes once. Projection places them with token substitution only and renders native files from the compiled `Method`.
- Every exported domain or application type is one line in `glossary.json`, under its one owning context.
- Types and ports that cross an arrow are contracts: a change to one is a change to every context that reads it, so it lands with the glossary and fixtures in one change.
- Fixtures are shape fixtures: real identities and frontmatter values, abridged prose and file bodies, references that may point outside the fixture. Never shape production output to match fixture bytes; exact outputs are proved by the goldens in `tests/golden/` (see `PARITY.md`).
- Unit tests touch nothing real: no repository folder (`core/`, `plugins/`), no temp folder, no process. A unit that reads files takes its context's narrow port and its test passes `createInMemoryFileSystem` from `src/kernel/fixtures/`. Only a registered platform implementer (today `src/kernel/file-system.ts`) has one hermetic test, in a temp folder it creates and removes.
- `src/` sits beside `core/` and `scripts/`: `core/` is projected content, `scripts/` is build-only, and runtime contexts ship through Packaging's `ToolBundler`.
- Typecheck: `bunx tsc --noEmit -p src/tsconfig.json`. Tests: `bun test ./src`. `tests/run-tests.ts` discovers every `src/**/*.test.ts` and runs it in the integration tier, named `src-<path>` (`--filter '^src-'`).
